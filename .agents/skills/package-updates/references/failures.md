# Failure taxonomy: what a red check means and what to do

Built from three weeks of sessions on api and frontend Renovate PRs (Sept 2026). The rule of thumb
that held up: **the failure decides the action, not the PR**. Read the failing job first, then act.
`scripts/failures.sh` matches `scripts/flake-signatures.tsv` against isolated Mocha/Cypress failure summaries.
For other log formats, it prints explicitly incidental whole-log hints: these are not a diagnosis
and do not justify a retry. Passing tests can intentionally emit deadlocks and schema errors;
this file is the reasoning behind each class. Keep the two in sync when you learn a new signature.

## Flaky vs real: the checks that settle it fast

1. Is main red on the same job today? `gh run list -R $REPO --branch main --limit 8 --json conclusion,createdAt,displayTitle,workflowName`. Main red on the same spec means rerunning PRs is pointless; find the fix or the external cause.
2. Did the same branch pass this job on the previous attempt or commit? `gh run view <run> --json jobs` shows attempts by `startedAt`.
3. Does the failing spec touch anything the bumped package does? Do not assume a patch bump cannot affect a spec; trace the exercised code path.
4. Is there a sibling PR with the identical diff (Renovate + Dependabot both bumping the same package) and is it green?
5. Local Jest on rest hits a live API: two `members › for event` tests fail on every branch locally (the event's members don't exist in that API's data), and the transaction suites time out under a full run but pass alone. Before blaming a branch, rerun the failing suite alone, then run it on `origin/main` in a second worktree; only a difference counts. Images is similar: its Jest suite runs against a live API and images server (`scripts/run_test.sh`), and in CI that API is **api main**, so a red images `test` can be an api-side break.
6. **A failure that repeats on retry needs investigation.** The user's rule: "it has to be related if it keeps failing, retry one more time perhaps? Then investigate."

## WebAuthn ASN.1 schema registry mismatch

Observed in [API #12199](https://github.com/opencollective/opencollective-api/pull/12199), fixed by
[6e41406ae](https://github.com/opencollective/opencollective-api/commit/6e41406ae), repeating the
[September 22 fix](https://github.com/opencollective/opencollective-api/commit/c678863e9).

**Signature:** the ES256 assertion test fails with `Cannot get schema for 'ECDSASigValue' target`
inside `@simplewebauthn/server`'s `unwrapEC2Signature`. This is not a GraphQL schema mismatch or
a database flake. Deadlocks and deliberate GraphQL errors elsewhere in the test log can be incidental.

**Cause to check:** `AsnParser` and the ECC schema class resolve different physical copies of
`@peculiar/asn1-schema`, each with its own module-local registry. Lockfile maintenance upgraded
transitive ASN.1 packages to 2.10.0 while direct schema and X.509 dependencies remained pinned to
2.9.5. An unchanged package.json therefore did not make the update safe. Check existing regression
test comments and Git history early: this failure already had both a fix and coverage.

In the isolated PR worktree, install its exact lockfile and compare resolution from each consumer:

```js
const { createRequire } = require("node:module");
const server = createRequire(require.resolve("@simplewebauthn/server"));
const ecc = createRequire(server.resolve("@peculiar/asn1-ecc"));
console.log(server.resolve("@peculiar/asn1-schema"));
console.log(ecc.resolve("@peculiar/asn1-schema"));
server("@peculiar/asn1-schema").AsnParser.parse(
  Buffer.from("3006020101020101", "hex"),
  server("@peculiar/asn1-ecc").ECDSASigValue,
);
```

The tiny DER parse reproduced the exception without a database; the existing WebAuthn test
confirmed the real assertion-verification failure. Check release notes, then align **both** direct
`@peculiar/asn1-schema` and `@peculiar/asn1-x509` pins with the compatible transitive version and
regenerate with npm. In this case, 2.10.0 removed duplicate registries. Do not blindly reuse that
version for future bumps, force incompatible overrides, or hand-edit the lockfile.

Verify one shared schema resolution, preserved unrelated lockfile updates, and the existing
`test/server/lib/two-factor-authentication` suite, plus type, lint, and format checks. The before
run had 7 passing / 1 failing WebAuthn tests; after alignment all 32 2FA library tests passed.
Keep fixes in a scratch worktree and preserve their commits during later rebases; once the fix
is pushed, the Renovate checkbox can discard it, so subsequent rebases must be local.

## Reading logs

`scripts/failures.sh` handles the common path. When you need the raw log:

```sh
gh run view -R $REPO --job <job-id> --log            # --log-failed is empty for cancelled/timed-out jobs
gh api --allow-escape-sequences repos/$REPO/actions/jobs/<job-id>/logs   # when the run is still in progress
gh api repos/$REPO/actions/jobs/<job-id> --jq '.steps[] | select(.conclusion!="success" and .conclusion!="skipped") | .name'   # which step
gh run download <run-id> -R $REPO -p 'cypress-recordings-*' -D <dir>    # screenshots: the fastest way to understand an e2e failure; Read the PNG
```

Log lines are prefixed `<job>\t<step>\t<timestamp> ` and carry ANSI colour; strip with `cut -f3- | perl -pe 's/^\S+ //; s/\e\[[0-9;]*m//g'`.
Always ignore: `##[error]Not Found - .../git/refs#get-a-reference` (the same-named-branch probe), `role "root" does not exist`, `GRAPHQL_ERROR_DETAILED`, `Random PayPal failure`, `Terminate orphan process`.
Download or read the log **before** rerunning: a rerun replaces it.
Logs older than about 90 days are gone (HTTP 410).

GitHub CLI can render ANSI escapes as literal `^[[31m` rather than raw escape bytes.
`failures.sh` strips both forms before finding failure summaries. If a coloured Cypress summary
is missed, inspect the cleaned text before relying on whole-log hints. In #12199 after the ASN.1
fix, the remaining E2E failure was the known `27-expenses.test.ts` invoice checkbox timeout
(`unchecked` versus `checked`), not a WebAuthn recurrence; verify the exact assertion before retrying.
